# Проверка GamePixel перед коммитом и выкладкой

Игру тестирует ребёнок на телефоне, а родитель узнаёт о новых возможностях только из справки в родительской зоне
(«Что умеет игра — подсказки для ребёнка»). Механика, которой там нет, для семьи почти не существует: ребёнок её не нашёл,
родитель о ней не знает. Поэтому «готово» здесь означает четыре вещи сразу: справка знает о новом, игра собирается,
тесты проходят, журнал дописан. Шаги идут от быстрых к долгим — первая же ошибка экономит семь минут тестов.

## 1. Справка для родителей (секунда)

```bash
node .claude/skills/gamepixel-release-check/scripts/check_help.mjs
```

Скрипт читает исходники и сверяет три списка: счётчики механик, которые код отправляет в статистику
(`this.stat('x')`, `statHit('x')`, `hintDone('x')`, а во снах — `s.tried('x')`), их подписи в родительской зоне
(`FEATS` в `game/src/parent.js`) и строки справки (`HELP` в `game/src/help.js`). Каждое расхождение он называет
и говорит, куда что дописать. Код выхода 1 — исправить и запустить снова.

Чего скрипт не видит: механику, у которой нет счётчика вовсе. Поэтому, закончив фичу, сверь её с этим списком:

- **счётчик** — `this.stat('имя')` (или `hintDone('имя')`, если у фичи есть подсказка-облачко; во сне — `s.tried('имя')`);
- **подпись** — строка в `FEATS` (`parent.js`): так счётчик читается в статистике «Чем пользуется»;
- **строка справки** — `['имя', 'что сделать', 'что будет']` в нужной группе `HELP` (`help.js`); для мира снов ключ `d:мир.имя`.
  Пиши так, чтобы родитель мог повторить действие, не видев игры: что взять, куда нести, что произойдёт;
- **подсказка для ребёнка**, если фичу трудно найти самому: запись в `HINTS` (облачко-цепочка; общие — в `core.js`, у комнат и локаций — свои `*_HINTS`, подмешиваются в `core.js`), строка в `LURES`
  (подпрыгивает, пока не трогали), во сне — `lures` мира;
- **сценарий в `game/tests/e2e.mjs`**.

Если счётчик — не действие ребёнка (итог, служебная отметка), впиши его с причиной в `NO_HELP` в начале скрипта:
молча пропущенный счётчик через месяц выглядит как забытая механика.

## 2. Сборка

```bash
cd game && npx vite build --logLevel error
```

Ошибка сборки — это почти всегда опечатка в только что написанном; чинить до тестов.

## 3. Тесты (полный набор ≈ 15–20 минут под нагрузкой, в фоне)

```bash
cd game && npm run test:e2e           # все сценарии (порт 5319, другой — E2E_PORT=…)
cd game && npm run test:smoke         # 10 ключевых, ~4 мин; его же запускает tools/deploy.sh
```

Комнаты в тестах — по именам (`window.__dev.R.yard`), не по номерам: игровая уже раз сдвинула ленту.

Запускай фоновой командой и жди уведомления. Пока тесты идут, **не меняй файлы в `game/`**: тестовый dev-сервер
перезагрузит страницу, и оставшиеся сценарии упадут по причинам, не связанным с кодом. Документы и память править можно.

Зелёные тесты проверяют состояние, а не то, что видит ребёнок. Если менялось что-то видимое (новый предмет, расстановка,
анимация, экран), посмотри на это глазами: сценарий на Playwright в scratchpad (`game/node_modules/playwright`,
окно 780×360, `deviceScaleFactor` 2–3, dev-сервер на свободном порту вроде 5320, управление через `window.__game`),
затем прочитай PNG. Так нашлись компост, вставший поверх качелей, и кукла, закрывавшая гриб.

## 4. Журнал

Допиши в `doc/specMagicPixelDollhouse.md` (раздел «Сделано…») что появилось и что попутно исправлено — по-русски,
словами для человека, который игру не открывал. По этому журналу потом восстанавливается, что и зачем было сделано.

## 5. Отчёт и выкладка

Сообщи пользователю итог по каждому шагу: что проверено и прошло, что упало (с текстом ошибки), что пропущено и почему.
Тесты упали — так и скажи, с выводом.

Выкладка (`tools/deploy.sh`) — только по явному слову пользователя в этом разговоре: она обновляет игру на телефоне ребёнка
и перезагружает страницу на всех устройствах. Сам `deploy.sh` тоже запускает проверку справки и остановится, если она не сходится.
Коммит — через скилл `commit`, не в `main`.
